## 0. Objective and Definition of Done

**Objective.** A customer opens any artwork and can buy it in **every LumaPrints product line**: stretched canvas (3 depths + rolled), framed canvas (3 depths, every frame style), fine art paper (all 7 papers), framed fine art paper (every frame profile, every mat width 1"–5", every mat color, glazing), foam-mounted paper, metal (both surfaces, all installation options), and peel & stick — choosing the options for their piece (frame color, mat size, mat color, paper, wrap, hardware…) with a live price and a live visual preview of the artwork in the chosen frame/mat. Margaret can switch **any medium, any option group, any individual option** on or off from the admin without a deploy.

**Definition of Done — all of the following, verified by the protocol in §10:**

1. Customer flow works end-to-end for **all 8 mediums**: artwork → medium → size → options → preview → priced cart line → checkout → paid order → automatic LumaPrints submission → tracking email. (Flow: see §7.)
2. Every LumaPrints option group for every enabled subcategory exists as a row in our DB with an **admin toggle** (medium ▸ subcategory ▸ option group ▸ option — four levels). Toggle coverage matrix in §8 is fully populated with zero "not toggleable" cells.
3. Pricing is correct for every (subcategory × size × option set): wholesale = base + Σ option deltas from the live pricing API, retail = (cost + worst-case shipping) × markup chain, proven by the full-matrix sandbox sweep (V2) and spot-checked against the LumaPrints dashboard on production keys (V7).
4. Orders submit with the customer's exact options (`orderItemOptions` + `solidColorHexCode` when applicable) and are accepted (201) — proven per-medium in sandbox (V4).
5. Two cart lines for the **same artwork+size with different options** coexist, price, and fulfill independently (V5/V6).
6. Disabling any option/group/subcategory/medium: hides it from the PDP immediately, blocks it at checkout validation with a friendly message, and **never breaks an already-paid order** (frozen snapshots still fulfill) (V5).
7. No regression for the 275 existing variants, existing carts, or the live launch config: the current black-frame 1.25" framed canvas and 1.25" canvas keep selling throughout the build (V6 regression suite).
8. The verification report (`audit/CATALOG-VERIFICATION-REPORT.md`) is generated by scripts, not hand-assertions, and every line is green before the launch toggle flips.

**Explicitly in scope:** everything above. **Explicitly out of scope (named so nothing is silently dropped — see §11 for why and for the hook left in place):** production-time upgrades (nextday/sameday), customer-chosen shipping method upgrades, international checkout, peel-&-stick *murals* larger than 49×150" (panelized product), and Margaret-supplied lifestyle photography for previews (the build ships a full synthetic preview; her photos can replace assets later).

## 1. Current State (verified against code + production DB, 2026-09-16)

Facts below were verified by direct code reading and a read-only production query; citations are file paths in the repo and live DB values.

**What exists and works today**
- Two customer-sellable mediums: `canvas` (subcat 101002, options `[2,11]` = Mirror Wrap + sawtooth) and `framed_canvas` (102002, options `[27,2,28]` = black floating frame + Mirror Wrap + wire). `src/lib/pricing/mediums.ts:102-121`.
- **All 8 mediums are already synced in production `lumaprints_mediums`** (queried 2026-09-16): canvas 101002 `[2,11]`, framed_canvas 102002 `[27,2,28]`, fine_art_paper 103001 `[39]`, framed_fine_art_paper 105005 `[64,74,83,94,96,146,148]`, foam_mounted 108001 `[39]`, metal 106001 `[31]`, peel_and_stick 107001 `[]`, rolled_canvas 101005 `[2,19]` — each with a ~23-size wholesale grid, all `enabled=true`, last synced 2026-06-10. So subcategory resolution + base pricing groundwork exists for every medium; what's missing is everything around *options*.
- Order pipeline: checkout freezes a `purchaseSpec` (incl. `subcategory_id`, `option_ids`) into `checkout_snapshots` → Stripe webhook writes `order_items` snapshot columns (`medium, size_label, print_width_in/height_in, lumaprints_subcategory_id, lumaprints_option_ids, print_storage_path, purchase_spec`) → `src/lib/fulfillment/router.ts` submits snapshot-first with claim/idempotency/retry discipline → shipping webhook advances to shipped. **This freeze path already carries per-item option arrays end to end** — it is just only ever fed the per-medium default.
- Pricing engine: `lumaprints_pricing_cache` (24h TTL) + live `/pricing/products` for custom sizes + 4-corner worst-case CONUS shipping + markup chain (variant → product → category → site). `src/lib/pricing/lumaprints-cache.ts`, `variant-pricing.ts`.
- Crop pipeline: one padded, aspect-exact PNG print master per artwork (`master_artworks.print_storage_path`), lossless, versioned. `src/lib/artwork/crop-worker.ts`.
- Production DB: **0 orders / 0 order_items** — the order-path reshape carries no live-data migration risk. 275 `product_variants`, 39 masters, 4 carts.

### Cross-cutting facts every phase builds on (P0, sandbox, 2026-09-16 — full evidence in `fixtures/lumaprints/PROBES.md`)
1. **Never send an empty options array** (P15): `[]` resolves to Image Wrap on canvas and 0.25in Bleed on paper, both of which 406 an aspect-exact master. Every seed, quote, shipping call and order sends the explicit geometry-neutral default set; `is_default` encodes Mirror Wrap / No Bleed, never the provider default.
2. **Pricing enforces nothing geometric** (P4, P8, P9): it prices past published max bounds, past the glass ceiling, easels at non-whitelisted sizes, and mat colours with No Mat. Bounds, glass ceiling, whitelist and dependency rules are enforced by `rules.ts` at PDP, quote, checkout and pre-submit — the provider will not stop a bad configuration before it is paid for.
3. **Group membership IS enforced** (P10, P11): a foreign option id is rejected with "not associated to subcategory", so per-subcategory option lists need no special-casing.
4. **Mats do not change the submitted size** (P3): width/height = print size, `expectedAspectRatio` = print aspect, the frame grows around the mat. `checkImageConfig`'s `recommendedWidth/Height` are inches × 25, not pixels.
5. **`checkImageConfig` normalises orientation** (P4): a landscape file passes a portrait order. Our own aspect check compares orientation-aware; the API will not catch a rotated master.
6. **Fractional inches work on every endpoint** (P7: single, batch, shipping, image check, order) despite the integer-typed batch schema → no per-endpoint fallback needed; F15 closed.
7. **Frame-style deltas are size-invariant; mat deltas vary by size** (P13) → cache per (subcategory, size, options) as designed.
8. **Order echo** (P16): submit `201` is a queue ack — `GET /orders/{n}` 404s immediately after and must be polled; option ids and fractional dimensions echo exactly; `solidColorHexCode` is NOT echoed — our snapshot is the only record of the chosen colour.
9. **Solid Color Wrap + hex is accepted end to end** on an aspect-exact master (P6, sandbox order 10000339585).
10. **Required groups** (P1): exactly three subcategories reject `[]` — the three framed-canvas depths (their Frame Styles group). Everything else, including all 25 framed-paper profiles, prices with defaults; `required` is seeded from this fact, not from id arithmetic (F13).

### The three catalog axes we must not conflate
1. **Medium** (customer-facing family, 8) — marketing copy, PDP grouping.
2. **Subcategory** (LumaPrints pricing/ordering unit) — canvas DEPTH (101/102), paper TYPE (103/108), frame PROFILE (105), metal SURFACE (106); bounds, DPI, base price live here.
3. **Option** (per-subcategory, grouped) — additive price (or whole-config where P0/V2 prove otherwise, §5 ADR-3), geometry effects, toggles live here.
Today's code collapses all three into one row. The schema in §4 separates them.

## 4. Data Model

### 4.1 New tables

```sql
-- One row per LumaPrints subcategory we can sell. The pricing/ordering unit.
create table lumaprints_subcategories (
  id                uuid primary key default gen_random_uuid(),
  medium            text not null references lumaprints_mediums(medium),
  subcategory_id    int  not null,           -- LumaPrints id (env-specific!)
  api_host          text not null,           -- 'us.api.lumaprints.com' | sandbox; §9 F12
  name              text not null,           -- LumaPrints name, e.g. '1.25in Stretched Canvas'
  display_label     text not null,           -- customer label, admin-editable
  description       text,                    -- PDP copy, admin-editable
  min_width_in      numeric not null,
  max_width_in      numeric not null,
  min_height_in     numeric not null,
  max_height_in     numeric not null,
  required_dpi      int not null,            -- from GET /subcategories
  max_glass_w_in    numeric,                 -- framed paper: glass ceiling if ≠ bounds
  max_glass_h_in    numeric,
  enabled           boolean not null default false,   -- admin toggle (new = OFF)
  sort_order        int not null default 0,
  customer_note     text,                    -- e.g. metal trim caveat, foam warp advisory
  pricing_mode      text not null default 'additive',  -- 'additive' | 'whole_config' (§5 ADR-3 / F26; flipped by V2 when a configuration is not additive)
  last_synced_at    timestamptz,
  unique (api_host, subcategory_id)
);

create table lumaprints_option_groups (
  id                uuid primary key default gen_random_uuid(),
  subcategory_ref   uuid not null references lumaprints_subcategories(id) on delete cascade,
  group_key         text not null,           -- normalized from API optionGroup name
  api_group_name    text not null,           -- verbatim
  display_label     text not null,           -- admin-editable
  required          boolean not null default false,  -- must submit exactly one (frame styles; from probes)
  customer_visible  boolean not null default true,   -- false = admin-pinned (e.g. hardware default)
  enabled           boolean not null default false,  -- admin toggle
  display_kind      text not null default 'list',    -- 'swatch' | 'list' | 'radio'
  depends_on_group  text,                    -- group_key whose selection gates this group's visibility
  depends_hidden_when jsonb,                 -- option_ids of the sibling group that hide this one (e.g. Mat Color hidden when Mat Size = No Mat)
  sort_order        int not null default 0,
  unique (subcategory_ref, group_key)
);

create table lumaprints_options (
  id                uuid primary key default gen_random_uuid(),
  group_ref         uuid not null references lumaprints_option_groups(id) on delete cascade,
  option_id         int  not null,           -- LumaPrints id (env-specific)
  api_option_name   text not null,           -- verbatim
  display_label     text not null,           -- admin-editable ('Walnut floating frame')
  enabled           boolean not null default false,  -- admin toggle
  is_default        boolean not null default false,  -- exactly one per enabled required/visible group
  sort_order        int not null default 0,
  swatch            jsonb,   -- {color_hex?, image_path?, frame_face_in?, frame_depth_in?} for preview
  geometry          jsonb,   -- see §5 ADR-4: {per_side_in?, requires_file_bleed_in?, size_whitelist?, needs_hex?}
  removed_from_api  boolean not null default false,  -- sync tombstone, §5 ADR-7
  unique (group_ref, option_id)
);
```

`lumaprints_mediums` is **kept** as the family table (labels, sort, family-level `enabled` toggle, marketing copy); its `subcategory_id`/`option_ids`/`sizes` columns become legacy-read-only after P5 cutover and are dropped in P8. ## 5. Architecture Decisions (ADRs)

**ADR-1 — DB-driven catalog; code carries no LumaPrints ids.** All subcategory ids, option ids, bounds, DPI, group structure, and constraints live in the three new tables, written only by sync v2 from the live API. The only compile-time list that remains is the 8-entry `MEDIUMS` family enum (labels/ordering); adding a 9th family is a one-line + copy change, and everything below family level needs zero deploys. Rationale: ids differ between sandbox and production (§9 F12), LumaPrints is in open beta and adds options, and "toggleable without redeploy" is a hard requirement.

**ADR-2 — Variant = size; subcategory + options are per-order state.** The sellable unit stays `product_variants` (product × medium × size, Live-gated, priced at default config of the medium's default subcategory). A customer **selection** = `{variantId, subcategoryRef, optionIds[], solidHex?}`. Cart line identity = `variantId + line_hash`, where **`line_hash = sha256(subcategoryRef ‖ sorted optionIds ‖ solidHex)`** — the subcategory is inside the hash because sibling depths share option ids (`[2,11]` on every canvas depth): identity by options alone would merge a 0.75″ and a 1.5″ canvas of the same size into one line across cart merge, checkout dedupe, and the order_items key (§9 F23). This threads through: cart reducer key, **`quoted-prices.ts` re-quote application (keyed per line, not per variant — §9 F23)**, `/api/cart/track` payload, checkout request item schema v3 `{productId, variantId, quantity, subcategoryRef, optionIds[], solidHex?}`, dedupe rule (reject duplicate `variantId+line_hash`, not duplicate variant), `checkout_snapshots.items[].purchaseSpec` (subcategory + selected option_ids + labeled `print_options` in details), `order_items` insert key `(order_id, variant_id, line_hash)`, and the Stripe line-item title (option summary appended so two configurations are distinguishable on the hosted page, receipt, and Stripe dashboard — §9 F28). Rejected alternative: variant-per-configuration rows (state explosion: one 30×40 framed paper = 12 frames × 10 mats × 14 colors ≈ 1,680 rows per size per artwork).

**ADR-3 — Pricing = cached base + cached per-option deltas, quoted server-side, revalidated at checkout.**
- One `/pricing/products` batch call per (subcategory, size) returns base + each requested option's price; sync v2 and the quote path store the **per-option breakdown** so any configuration prices as `base + Σ enabled-selected deltas` without new API calls. **Additivity is asserted, not assumed**: P0 probes and every V2 maximal-config sweep check `apiTotal === base + Σ deltas` per configuration; any non-additive combination fails the gate and switches that subcategory to whole-config pricing rows (§9 F26). **P0 result (P14, 20 distinct-group configurations):** canvas and framed canvas are additive at every configuration (diff $0.00); **framed fine art paper is NOT** — the mat price depends on the paper and backing chosen (105005 3in mat + Somerset Velvet: predicted $62.84 vs API $65.64; 105001 2in mat + Kraft backing: $53.40 vs $53.55). So every 105xxx subcategory is seeded `pricing_mode = 'whole_config'`: the quote path prices the exact configuration through `/pricing/products` (batching all requested configurations per call) and caches per `(subcategory, size, price_key_hash)`; `base + Σ deltas` is used only where `pricing_mode = 'additive'`. Single-group subcategories (metal, paper, foam, peel & stick) are trivially additive. Cache row per `(subcategory, size, price_key_hash)` with breakdown; 24h TTL kept; sync evicts per subcategory; **toggling an option also evicts that subcategory's quote rows** (fixes G6/cache-staleness). The quote path handles LumaPrints 429s with backoff-and-retry and serves the last cached row with a staleness bound rather than failing the PDP (§9 F29).
- Displayed price = `(config cost + worst-case CONUS shipping for that config) × markup chain` — same markup resolution as today (variant → product → category → site). Worst-case shipping is quoted per configuration but bounded: the quote endpoint memoizes shipping per `(subcategory, size, shippingClassHash)` where shippingClass = options that plausibly change weight/box (frame, glazing, backboard, posts — flagged in `geometry`); mats/colors don't re-quote. AK/HI continues to re-quote live at checkout (existing `shipping.ts` path, now with selected options).
- The PDP never computes money client-side: `POST /api/products/[id]/print-quote {medium, variantId|size, optionIds}` → `{available, priceCents, compareNote?, constraintViolations[]}`. Rate-limited (existing `rate_limit_buckets`), cache-backed, and **the same server module is called again inside checkout validation** — one source of truth, so PDP price ≡ charged price or checkout blocks with a re-quote message (§9 F9).

**ADR-4 — Geometry rules engine (`src/lib/catalog/rules.ts`): dimension math only, never re-rendering.** The padded print master's aspect is the invariant; every option's physical effect is declared in `lumaprints_options.geometry` and enforced identically at PDP, quote, checkout, and pre-submit. **P0 proved the provider enforces none of this before payment** (pricing accepts out-of-bounds sizes, over-ceiling mats, non-whitelisted easels and mat colours without a mat — P4/P8/P9), so the engine is the only gate:
- `per_side_in` (framed-paper mats, P3-confirmed): the submitted LumaPrints `width/height` stays the PRINT size and the frame grows around the mat; glass = print + 2×value per axis. Constraint: glass ≤ the subcategory's max bounds (`max_glass_w_in/h_in` = the API's `maximumWidth/Height`: 36×24 for the three 0.875×0.875 profiles, 60×40 for the other 22), orientation-aware. Mat widths that would exceed it for the chosen size are **disabled with a reason string** in the UI and rejected server-side.
- `requires_file_bleed_in` (Image Wrap +3.75in/axis, option 1 on every canvas subcategory) **and every non-zero paper `Bleed Size` option (36/37/38)**: P5 showed the API expects an image of (ordered − 24×bleed) per axis for bleed — geometrically wrong and negative at 1in — so bleeds get the same treatment as Image Wrap: the admin toggle exists but flipping it ON is blocked with the explanation ("needs a print file with bleed; the crop pipeline intentionally never crops artwork content"). They ship OFF, visible, documented; No Bleed (39) and Mirror Wrap (2) are the only enablable members and the seeded defaults. (Recorded path if ever wanted: a crop-worker render mode — out of scope, §11.)
- `size_whitelist` (Metal Easel, option 32): offerable only when `(w,h)` ∈ {8×10, 8×12, 11×14, 11×17, 12×12, 12×16 portrait, 16×24 landscape} (lumaprints.com; the API prices it anywhere — P9). Enforced same three places.
- `needs_hex` (Solid Color Wrap, option 3): requires `solidHex` (`#rrggbb`), which flows selection → snapshot → `order_items.solid_color_hex` → `submitOrder` payload `solidColorHexCode`. The provider never echoes the hex (P16), so the snapshot is the record and V4 asserts it from our DB, not from the provider.
- `probe_owed` (Rolled Canvas Border Size 19–22): not image-checked in P0; the toggle is ◼ until V3 records `checkImageConfig` 200 per option with an aspect-exact master.
- Group rules: `required` groups need exactly one selection (server auto-fills the default if the group is admin-hidden) — seeded from P1 (only the three framed-canvas Frame Styles groups); `Mat Color` is dependent-visible (only when Mat Size ≠ No Mat) via `depends_on_group` — and server-rejected otherwise, because the API accepts the pair silently (P8); hardware / underlayer / finish constraints per depth arrive naturally because option lists are per subcategory and the API rejects foreign ids (P10/P11) — no special casing.
- **Never send `[]`** (P15): every provider call carries the explicit default of every group the customer did not touch; `rules.ts` fills those defaults.
- Our own aspect check is orientation-aware (compare w:h AND orientation of master vs order), because `checkImageConfig` normalises orientation (P4) and would pass a rotated master.
- Replaces `isFramedSubcategory` id-arithmetic (`fulfillability.ts:41`) with the data-driven `required` flag — this also closes the latent bug where framed *paper* (105xxx) escaped the frame-required check (and P1 shows framed paper needs no required group at all: the profile is the subcategory).

**ADR-5 — Toggle semantics & cascade.** Four levels, each `enabled` boolean: medium (family) → subcategory → option group → option. Effective availability = AND of the chain. Rules: disabling a subcategory hides its variants' *print offerings* (variants stay in DB); disabling a required group's every option auto-blocks the subcategory with an admin banner (can't sell a framed canvas with zero frames); exactly-one `is_default` per enabled visible group is DB-constraint-enforced (partial unique index) with admin UI repair; **paid orders are immune** — fulfillment reads only the frozen snapshot (already true in `router.ts:209-212`; P6 adds a test that a disabled-after-purchase option still submits); carts re-validate at quote/checkout and get a per-line "this option is no longer available" resolution UI rather than a silent price change.

**ADR-6 — Preview is a layered client compositor, no external mockup service.** LumaPrints has no mockup API. `FramePreview` renders, back to front: wall backdrop → frame rectangle (from `swatch.color_hex` or a 9-slice corner `image_path` when the admin uploads one) with face width scaled from `swatch.frame_face_in` → mat rectangle (mat color hex, width scaled from `per_side_in`) → the artwork's existing web image (already cropped to print aspect) → canvas-depth edge hint for wraps (mirror = blurred edge reflection, solid = hex). True-to-scale within the frame: all inches map through one px/in scale so an 8×10 with a 3" mat visibly grows. Every enabled frame/mat option must carry a swatch (sync seeds `color_hex` from name-matching; admin can refine; the catalog manager flags enabled options with missing swatches — a V6 gate). Also renders the size-on-wall hint (existing dimension data). This is deterministic, works for all 39 artworks with zero per-artwork asset work, and Margaret can later drop in photographic corner assets per option without code.

**ADR-7 — Sync v2 = structure sync with merge, never a state reset.** Sync walks categories → subcategories → options per subcategory (the existing `discover-lumaprints-catalog.mjs` logic productionized), then **merges**: new subcats/groups/options inserted `enabled=false` + admin "NEW" badge; existing rows update API-sourced fields only (name, bounds, DPI, prices) and never touch `enabled/is_default/display_label/swatch/sort`; options missing from the API get `removed_from_api=true` + owner alert (never deleted — order history references them; `enabled` is the admin's field and a tombstone never touches it — the availability cascade hides a tombstoned row, and a row the provider brings back keeps the admin's configuration; P1 security pass). Finalize refuses to tombstone when a run saw fewer than half the host's known subcategories (a truncated or empty provider answer fails the run instead of switching the catalog off). Sync also refreshes each enabled subcategory's base-price grid and evicts caches. Runs: manually from the catalog manager (with dry-run diff view), and weekly via a new cron (`/api/cron/lumaprints-catalog-sync`, CRON_SECRET-guarded like the others) so a LumaPrints catalog change surfaces as a badge, not a 406 at order time. **Execution model (§9 F24):** a full walk plus price-grid refresh is 70–150+ API calls — minutes of wall time that cannot fit one serverless invocation (house `maxDuration` is 60s). Sync v2 is therefore **chunked and resumable**: a `catalog_sync_runs` cursor row in DB, one category (or one subcategory price-grid) per invocation, the cron self-re-invoking until the cursor completes, every chunk's merge transactionally safe so a timeout never leaves a half-merged catalog; the admin button starts a run and shows progress, never blocks on completion. Rate-limit budget: sync throttles to **≤25 req/min, leaving ≥15/min headroom for live PDP quotes and checkout re-quotes** on the shared key, and the cron is scheduled 03:00–05:00 CT (§9 F29).

**ADR-8 — Storefront cutover behind a flag, per-medium go-live.** `site_settings.print_configurator_enabled` gates PrintConfigurator vs the legacy dropdown (both code paths ship). Catalog rows launch with only today's config enabled (§4.3), so flipping the flag is behavior-neutral by construction; each new medium/option then goes live by admin toggle, not deploy. Rollback at any moment = flip the flag back; data model is additive so the legacy path keeps working until P8 cleanup.

## 9. Adversarial Findings (pre-mortem) and their answers in this plan

Each finding is something that would have caused a "why doesn't X work" moment after a naive build. F-numbers are referenced from the phases/tests.

- **F1 — Same-variant/different-options collisions.** FIVE independent layers assume line=variant: cart reducer key, checkout dedupe, `order_items` upsert key, cart-track payload, **and the `quoted-prices.ts` re-quote application** (server price re-stamping keyed by variant would price one of two same-variant lines wrong). Missing any one silently merges, drops, or misprices a line. → ADR-2 changes all five together; V5 has explicit dual-line tests.
- **F2 — Mat width silently invalid at big sizes.** 30×40 print + 5″ mat = 40×50 glass > some frames' 40×60?—fine, but 24×36 glass cap on the 0.875×0.875 profile makes even 20×30+2″ invalid. If unmodeled, customers hit LumaPrints 406 at fulfillment, after payment. → geometry `per_side_in` + per-frame glass caps enforced at selection time (ADR-4); P0 pins the exact constraint surface; V2 sweeps mats at edge sizes.
- **F3 — Paper bleed changes the printed-image aspect** (8×10 paper, 1″ bleed → 6×8 image ≠ crop aspect → distorted art or 406). A naive "enable all the toggles" build ships corrupted paper prints. → P0 probe decides; engine supports both semantics; default No Bleed (ADR-4).
- **F4 — Image Wrap needs +3.75″/axis of image content that aspect-exact masters don't have** (the exact bug class that 406'd launch night, per BUILD_LOG). → ◼ blocked-with-reason toggle; never silently absent, never enabled into failure (ADR-4).
- **F5 — Solid Color Wrap requires `solidColorHexCode`**, which the integration type already supports (`lumaprints.ts:156`) but nothing upstream ever populates — enabling the option without the P5/P6 threading = every order defaults to black sides. → hex threaded selection→snapshot→`order_items.solid_color_hex`→router; V4 sandbox order includes it.
- **F6 — Option prices vary by size** (a 3″ mat on 8×10 ≠ on 24×36), so caching deltas per option-alone would misprice. → cache keyed with size + breakdown per response (ADR-3); P0 probe confirms variance; golden tests per size.
- **F7 — Toggle flips leave stale cached prices/quotes.** → toggle handlers evict subcategory quote rows + bump the catalog cache tag (ADR-3/P1); V5 asserts fresh quote after toggle.
- **F8 — Disabling an option strands paid orders or in-flight carts.** → snapshot-immune fulfillment (test in P6); carts re-validate with per-line resolution UI, not silent repricing (ADR-5).
- **F9 — PDP price ≠ charged price drift** (cache refresh, margin edit, LumaPrints price change between browse and pay). → one quote module used by PDP and checkout; checkout re-quotes and blocks with a friendly per-line message on mismatch (ADR-3), mirroring the existing hosted-prices pattern.
- **F10 — Hardware/size/depth cross-constraints** (1.25″ = sawtooth-only; easel size whitelist; foamcore 1.5-only). Hardcoding these would rot. → they fall out of per-subcategory option lists + `size_whitelist` geometry; no special-case code (ADR-4).
- **F11 — 40 req/min rate limit** makes naive full-matrix syncs/sweeps fail exactly when run for launch. → throttled clients in sync + verify scripts; sweeps batch via `/pricing/products` (many sizes per call); budget math in each script header (P0/V2).
- **F12 — Sandbox and production option/subcategory ids may differ.** Building toggles against sandbox ids then launching on prod ids = wrong options submitted. → `api_host` column, per-host snapshots, P0 diff, launch config seeded from the **production** snapshot, verification V2/V4 run on sandbox ids resolved by *name-mapping through the two snapshots* with any unmapped row failing the gate.
- **F13 — Framed paper escaped the frame-required check** (`isFramedSubcategory` = 102xxx only): enabling framed paper today could submit frameless framed-paper orders. → data-driven `required` flag (ADR-4/P6 regression test).
- **F14 — Paper needs 300 DPI, code assumes 200 everywhere.** Sizes that fit canvas won't fit paper for smaller scans; if unhandled, either overpromised sizes (soft prints) or false "unavailable". → per-subcategory `required_dpi` from the API drives size generation and Live-gating (P2/P3); admin banner explains per-medium ceilings.
- **F15 — Integer-vs-fractional size typing differs per endpoint** (batch pricing/shipping schemas say integer). Existing fractional variants (0.05″ grid) must keep working on new mediums. → P0 probes fractional on every subcategory; quote path falls back to single-product pricing (number-typed) where batch rejects; recorded per-subcategory in PROBES.md.
- **F16 — Webhook replay + new insert key.** Changing the upsert key can break replay-idempotency (duplicate order items on Stripe retries). → key includes options_hash with same ignoreDuplicates discipline; V5 replay test.
- **F17 — Cart/localStorage migrations.** Persisted carts predate options; a hard schema break empties carts. → versioned cart state, legacy lines adopt hash '' (P5).
- **F18 — Preview lies.** A preview that shows a walnut frame when the walnut toggle maps to the wrong option id sells the wrong product. → swatch lives on the option row itself (id-bound); V6 E2E asserts label/swatch/order-payload agreement via a test order per frame family; enabled-option-without-swatch blocks in the catalog manager.
- **F19 — Metal sublimation trim + foam warp advisories** are physical-product facts customers must see before buying (returns risk). → `customer_note` per subcategory rendered on PDP (P3/P4).
- **F20 — Business-side stranding**: enabling a medium with zero Live variants, or a required group with zero enabled options, shows dead UI. → cascade guards + admin banners (ADR-5); availability computation excludes such subcats (P2).
- **F21 — Margins per medium.** Paper costs ~$4–15 vs framed canvas $28–100; one site-wide markup % produces silly paper prices. → markup chain already supports per-product/category overrides; §11 asks Margaret for per-medium defaults *before* enabling (launch-gate checklist item, not code).

Findings F22–F29 were surfaced by the independent adversarial review of rev 1 (archived alongside this plan) and are integrated above and in the phases; listed here so nothing lives only in a diff:

- **F22 — Snapshot-version gates (CRITICAL).** Seven hard `=== 2`/`!== 2` checks across the Stripe webhook (`:153` throws on non-2 → Stripe retries forever, zero orders; `:158`, `:167`, `:376` row-builder, `:951`/`:1333` fulfillability nets on legacy columns) and `snapshot.ts` would brick v3 order creation. → P5 gate sweep + V1 v3-through-every-path test.
- **F23 — Subcategory missing from line identity (CRITICAL).** Sibling depths share option ids, so options-only hashing merges "24×36 · 0.75″" with "24×36 · 1.5″" across cart/dedupe/order-key — different physical products, different costs. → `line_hash` includes subcategory (§4.2, ADR-2); dual-depth V5 test.
- **F24 — Sync can't fit one serverless invocation** at ≤40 req/min (house `maxDuration` 60s; walk+grids = minutes). → chunked cursor-resumable sync (ADR-7).
- **F25 — No storewide offer generation**: per-product tooling alone never gets 39 artworks × 6 new mediums live. → P3 offer-coverage generator + coverage report.
- **F26 — Delta additivity unproven**: quote engine sums cached per-option deltas; a non-additive combo (oversize surcharge, option interplay) misprices silently. → P0 probe + V2 assertion `apiTotal === base + Σ deltas`, fallback to whole-config rows.
- **F27 — In-app help contradicts the new store** (`articles.ts`: "does not order a physical mat board or choose a frame", "Frame is not included", 200-DPI guidance). → P8 rewrite pass.
- **F28 — Stripe surfaces can't distinguish configurations**: hosted checkout/receipts show `title` only; two same-variant lines look identical at different prices. → option summary appended to line-item titles (ADR-2/P5).
- **F29 — Shared 40/min key contention**: weekly sync saturating the budget causes customer-visible 429s at cache-miss quote time. → sync capped at 25/min in a dead-hours window; quote path gets 429 backoff + stale-serve (ADR-3/ADR-7).

**P0 verification results (sandbox, 2026-09-16; `fixtures/lumaprints/PROBES.md`, 16 probes, 6 PASS / 10 FINDING / 0 FAIL / 0 SKIPPED, 3 sandbox orders 10000339584–6):** F2 confirmed and worse — pricing enforces neither bounds nor the glass ceiling (engine-only gate). F3 resolved — bleed is BLOCKED, not per-side (the API expects a shrunken, even negative, image). F4 confirmed (Image Wrap 406). F5 confirmed accepted end to end; hex not echoed (our snapshot is the record). F6 confirmed for mats, refuted for frames (size-invariant). F10 confirmed provider-enforced. F13 confirmed: exactly 3 required-group subcategories (102001/102002/102003). F15 closed — fractional inches accepted on every endpoint. F26 confirmed for framed paper only — 16/20 distinct-group configurations additive; the 4 non-additive ones are all 105xxx (mat delta depends on paper/backing; max diff +$2.80), so every 105xxx subcategory gets `pricing_mode = 'whole_config'` (§4.1, ADR-3) and prices whole configurations through the API; canvas/framed canvas sum deltas. New findings: **F30** `[]` resolves to geometry-hostile defaults — never send it. **F31** the provider does not enforce whitelist / dependency / bounds at pricing — the rules engine is the sole pre-payment gate. **F32** `checkImageConfig` normalises orientation and reports `recommended*` in inches×25 — our aspect check is orientation-aware and never treats those fields as pixels. **F33** `GET /orders/{n}` 404s right after a 201 — V4 and the status cron poll. **F34** catalog structure beyond rev 2: Canvas Finish group, Framed-paper Backing + Print Mounting groups, Paper Type as an option on 105, Foam-mounted Canvas 108010, Metal surface as the subcategory axis, Glossy Silver's narrower bounds, Rolled Canvas Border Size geometry unprobed — all DB rows, all toggleable (§8). **F12 CLOSED (P0b, production snapshot captured through the deployed admin route on 2026-09-17 UTC, `fixtures/lumaprints/catalog.us.api.lumaprints.com.2026-09-16.json` + `id-diff.2026-09-16.md`):** 1,239 rows match by name with the SAME id on both hosts, 0 same-name-different-id rows. Only two differences: production has one extra framed-paper profile, `105021` 3.250w × 1.375h Vintage Collection Copper Frame (26 profiles vs 25 in sandbox — a DB row like any other), and category 108 is named "Foam-mounted Print" in production vs "Foam-mounted Fine Art Paper" in sandbox (same id 108, same 8 subcategories). Sandbox-verified option ids are therefore valid launch config for production; `api_host` stays as the safety column and sync v2 writes per host.

Assumptions that remain (stated, not hidden): LumaPrints keeps the documented API shapes (open beta — the weekly sync + alerts are the tripwire); one print master serves all mediums (true today; paper's higher DPI only narrows sizes, never changes files); US-only stays; production billing address remains configured in the LumaPrints dashboard (order 400 otherwise — verified live during the July launch).

## 10. First-Try Verification Protocol

Principle: **every Definition-of-Done clause maps to a machine-run check**; the launch gate is a generated report, not confidence. All scripts write structured results into `audit/CATALOG-VERIFICATION-REPORT.md` (one section per V-step, timestamped, with raw counts and every failure enumerated). A step is green only at 100% of its assertions; documented per-size drops (out-of-bounds) are listed, not counted as failures.

**V1 — Contract & fixture tests (CI, every PR).** Sync merge semantics, catalog loader cascade, rules engine matrix (every geometry key), pricing math goldens per medium (from P0 fixture prices), selection validation matrix (every rejection reason), options-hash stability, snapshot v2/v3 coexistence, webhook replay with new key, 105xxx-frame-required regression, disabled-after-purchase fulfillment. Runs in `npm test`; the suite list is the file-level checklist for P1–P7.

**V2 — Full-matrix sandbox pricing sweep** (`scripts/verify-catalog-pricing.mjs`). For every subcategory in the sandbox snapshot: price the full size grid at default options (batch), plus each enabled option one-at-a-time at 3 representative sizes (small/mid/max), plus the maximal configuration at 2 sizes. Assert `success:true`, cost > 0, per-option deltas present, **whole-config additivity (`apiTotal === base + Σ deltas`) on every maximal configuration** (F26), and (for mats) glass-bound edge behavior matches the rules engine's prediction. Throttled ≤40/min (≈25–35 min run). Output: per-subcategory table of priced combinations. Re-run against **production keys in read-only mode** (pricing endpoints only) to catch prod/sandbox divergence (F12) — pricing calls place no orders.

**V3 — Geometry sweep** (`scripts/verify-catalog-geometry.mjs`, extends P0's probes). For each geometry-bearing option (every mat width, each bleed, wraps, easel): `checkImageConfig` with a real padded master URL at in-bound and edge sizes; assert 200 with `expectedAspectRatio` matching the rules engine, and 406 exactly where the engine predicts unavailability. This is the check that the *math we show customers* equals the *math LumaPrints enforces*.

**V4 — Sandbox order suite** (`scripts/verify-catalog-orders.mjs`, store 82222). One order per medium (8 total), maximal-option configurations (framed paper: decorative frame + 3″ mat + colored mat + glazing; canvas: solid-color wrap + hex + backboard hardware; metal: silver + easel at a whitelisted size; etc.), fractional size on at least two. Assert 201, then `GET /orders/{n}` echoes exact `orderItemOptions`/hex/dimensions; then simulate the shipping webhook against a preview deploy and assert item → shipped + email render. Cancel/ignore sandbox orders afterward per sandbox norms.

**V5 — Money-path integration tests** (CI + preview deploy, Stripe test mode). Dual-line same-variant order **including same-size different-depth** (F23); per-line quoted-price application on dual lines (F1); v3 snapshot through every webhook path incl. replay (F22); toggle-off between add-to-cart and pay (blocked with message); price-drift re-quote; cart migration from legacy persisted state; AK/HI option-aware shipping quote; discount/tax unchanged on option-bearing lines; Stripe hosted-page line titles distinguish configurations (F28).

**V6 — E2E storefront suite** (Playwright against preview, flag ON). Per medium: full configure→preview→cart→checkout(test)→confirmation flow; disabled-option invisibility; dependent groups (mat color appears only when matted); per-size mat disabling with reason; a11y assertions on the configurator; **V6.1 regression**: legacy parity — with only today's config enabled, the PDP offers exactly today's choices at exactly today's prices (cents-diff script over all 275 variants), and originals/classes/commissions flows untouched.

**V7 — Production launch gate** (scripted checklist, each item auto-checked where possible):
1. Prod catalog sync run; zero unmapped rows vs sandbox-verified structure (F12 name-mapping); NEW rows all consciously toggled.
2. V2 prod pricing sweep green; spot-check 5 configurations against the LumaPrints dashboard UI prices (manual, recorded).
3. Margin defaults set per medium (§11 with Margaret) — gate refuses if any enabled subcategory has a config priced below cost+shipping.
4. Swatch completeness: no enabled frame/mat option without swatch; preview screenshot grid attached.
5. Billing address configured on the production LumaPrints account (order-400 guard); webhook subscription live (existing).
6. DB invariants query pack: exactly-one default per enabled required group; no enabled option under disabled group; no Live variant on disabled subcategory; cache hygiene.
7. Kill-switch drill: flip `lumaprints_enabled` off/on in prod, confirm pause/resume (existing behavior, re-verified).
8. Rollback drill on preview: flag off → legacy PDP returns.
9. **One real production order** (F12's only true closure): cheapest framed paper print with a maximal safe option set (frame + 2″ colored mat), live keys, shipped to Margaret as a QC sample (~$15 + shipping) — verified in the LumaPrints dashboard (options correct) before any new medium is enabled for customers, and the physical piece confirms frame/mat/color on arrival. Sandbox proves the code path; only this proves the production ids.
**GO** = every line green in the generated report. Then flip the flag (behavior-identical), then enable Margaret's launch selection medium-by-medium.

**V8 — Post-launch watch (first 2 weeks).** First-order-per-medium alert (extend existing owner alerts); daily cron already reconciles orders; weekly catalog sync surfaces upstream changes as badges; any `failed_validation` on a new medium pages the owner email with the item's frozen spec for one-look diagnosis. A standing instruction in the report: the first real order on each newly enabled medium gets manually eyeballed in the LumaPrints dashboard before the day ends.

## 11. Open Business Decisions (Margaret) — none block the build

All toggles/config, zero code: (1) which frame styles/mediums are visible at launch (build enables capability for all; she curates); (2) per-medium margin defaults (F21 — proposal table to review: paper/foam higher %, framed lower %, metal mid); (3) display labels/descriptions per subcategory (drafts provided, she edits); (4) whether to show "Glossy Silver" metal and decorative frames at launch or phase them; (5) preview asset upgrades (her corner photos later); (6) deferred-with-hook items: production-time upgrades and shipping-method choice (both are single enum fields already supported by `submitOrder` — exposing them is a future checkout surface decision, deliberately not smuggled into this build); international shipping (schema-level US pin stays).

## 12. Sequencing, Effort, Rollback

Dependency chain: P0 → P1 → P2 → {P3, P4 in parallel} → P5 → P6 → P7 → P8 → P9. Rough shape: P0 one focused session (mostly API-bound waiting); P1–P2 the heaviest engineering (schema+engine); P3–P4 the heaviest UI; P5 the most delicate (money path — smallest possible diff, every change behind the schema-version switch); P6–P7 small; P9 is mostly running the harness built along the way. Every phase lands as its own PR with its exit-criterion evidence in the description; BUILD_LOG entries per phase (house convention).

Rollback story at every stage: catalog tables are additive (ignore = today's behavior); storefront flag flips back instantly; checkout accepts snapshot v2 throughout, so even a mid-deploy cart completes; fulfillment reads frozen snapshots, so nothing about toggles or catalog state can strand a paid order; the global kill switch remains the last-resort pause. The one irreversible step — dropping legacy columns — happens only in P8, after a full release of dual-path operation.
